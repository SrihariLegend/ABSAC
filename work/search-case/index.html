The 32-Byte Ruler

A compiler found a loop that clang will not optimize, rewrote it to use the library call sitting right next to it, and made it 25× faster. Then its own test harness measured that rewrite as a loss, because the harness only ever feeds it inputs up to 32 bytes.

01The gap clang leaves open

A developer writes the ordinary linear search. It is correct, it is obvious, and it is one of the most common loops in C:

find_firstthe source
long find_first(const unsigned char *a, long n, unsigned char c) {
    long i;
    for (i = 0; i < n; i++)
        if (a[i] == c) return i;
    return n;
}

Told to compile it as fast as it can, clang emits this:

ABSAC, definition 403vectorized path
static uint64_t __sir_memchr(
        const uint8_t *base, int key, uint64_t n) {
    if (n == 0) return 0;
    uint64_t head = n < 16 ? n : 16;
    for (uint64_t i = 0; i < head; i++)
        if (base[i] == (uint8_t)key) return i;
    if (n <= 16) return n;
    const void *hit = memchr((const void *)(base + 16),
                            key, (size_t)(n - 16));
    return hit ? (uint64_t)((const uint8_t *)hit - base) : n;
}

An early-exit search returning an index has a trip count that depends on the data, so it does not vectorize, and LLVM has no memchr idiom recognition for it. Verified rather than assumed: clang -O3 -S on this function produces 0 memchr calls and 0 vector instructions. The library call is available, and clang will not use it.

ABSAC recognises the loop and rewrites it. Its emitted code is not a bare memchr call — it scans the first 16 bytes inline so an early hit avoids the call entirely, then hands the remainder to the vectorized library routine. That kernel is a compromise between the two costs, and it is not one a person writes by hand.

A 32-byte ceiling

The win is a function of scan length. It is a byte loop against a vectorized library call, and at n ≤ 32 there is no scan to vectorize. So the referee timed this rewrite at 0.82× — a loss — while the same rewrite at 64 KiB is 25.6×.

The harness did not measure the transformation. It measured the size guard. That guard is the first line of the emitted helper, and below 32 bytes it is the only line that runs.

This is the second time the same defect has been recorded for this project. The first was a kernel where the differential driver's input set decided what counted as correct. Here the timing driver's input set decides what counts as fast, and the consequence is the same: a real win reads as a regression.

It is very likely why this family has appeared useless. On the nineteen-benchmark corpus the search family never fires, and anyone reading the gate would conclude it does not pay. It pays. The ruler is 32 bytes long.

04What it does not do

The recognizer requires the not-found sentinel to be the scan bound. The loop must carry exactly (false, bound, 0), its result select must be found ? index : bound, and its termination must compare the index against that same carried bound.

So return n matches and return -1 does not — even though they are the same loop. The return -1 form lowers to a carried -1 with its termination against the parameter n, and the recognizer refuses it because the comparison never meets the carried value. Since memchr returns a pointer and index-based searches conventionally return -1, a large share of real instances are refused on the sentinel alone.

That is a recognition gap, not a proof gap, and it is the next thing to fix.

Scope

One function shape, tested at eight needle positions across thirteen sizes. Not a corpus. The win needs a long input with a late or absent hit: for a hit in the first 16 bytes the head scan makes it a wash, and for a hit at byte 0 it is strictly more work than the original.

And nothing here is a compiler result yet. The rewrite was verified on a hand-written kernel of the shape the family accepts — not discovered by lowering a third-party project. That is the test the project has not yet passed, and it is the one that would matter.

05Correctness, on both paths

The referee reports clean cases=500, mismatched=0 for definition 403 — the equivalence obligation plus a differential against the original.

But its differential draws from that same 32-byte list, so it never reaches the branch where memchr is actually called. The path the win is claimed on is the path it does not test. Checked separately: 90 configurations, 0 mismatches, across sizes 0 / 1 / 15 / 16 / 17 / 31 / 32 / 33 / 64 / 1000 / 65536 / 1 MiB / 4 MiB and needle positions {absent, 0, 15, 16, 17, 31, 32, n/2, n−1} — including every position where the head scan hands over to the library call.
